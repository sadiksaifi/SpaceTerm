# Use one headless executable

`spaceterm` runs the SpaceTerm Server and provides the command-line client for local and paired servers. It links no GPUI, GPU, display or Sparkle code, so server administration and terminal work need no desktop process. The desktop remains a separate executable under [ADR 0012](0012-derive-one-application-identity-from-the-build.md).

The signed headless artifact contains `server/bin/spaceterm`. Native service units invoke `spaceterm server run --service --identity <identity>` from the approved runtime. The foreground Development supervisor uses `server run --owned`; service and owned modes are mutually exclusive. Machine-facing provisioning, runtime verification, packaging checks and the transient service helper use hidden `server provision` commands. [The command tree](../../crates/spaceterm-cli/src/args.rs) owns this grammar. The CLI opens no SSH connection; [SSH Setup](0003-use-openssh-for-server-setup.md) remains a desktop operation.

The installer owns the command-line launcher in `~/.local/bin/`. It points to the approved runtime, or to the installation just retained when none is approved. [Launcher replacement](../../crates/spaceterm-server/src/service/runtime/launcher.rs) holds the service lock and replaces only a link into that identity's installations. A foreign executable or link stays untouched. The installer's hidden `server provision uninstall [--confirm TOKEN]` step stops and unregisters the service and removes only its managed launcher under that lock. There is no visible CLI uninstall command. [The installer](../../packaging/install.sh) owns its preview and confirmation journey, documented in [the local workflow](../local-server.md#install-the-command-line). Desktop and headless installation share one server under [ADR 0033](0033-reuse-one-server-across-headless-and-desktop-installations.md).

The service lock orders only SpaceTerm's own writers, so publication never replaces an entry another program creates meanwhile. A missing launcher is created exclusively; an existing entry there is kept. A managed launcher is exchanged atomically with the new link, and the exchange is reversed when it displaced anything other than that managed link. This applies to the installer and the desktop alike.

The desktop's Settings > Servers presents this launcher as the Command Line Tool row. Its Install uses the same launcher replacement through `Service::link_cli`. That call waits at most the one-second operation grace for the service lock, then reports a busy service. It follows the approved runtime. Without one, it first retains the desktop's own signed server package, which registers and starts no service. Install writes only the account's own `~/.local/bin`, so it needs no administrator authorization, password or credential store. A link elsewhere and a file that is not a link stay untouched; the row names either and offers to show it in the file manager, which reports whether it could. The row makes no claim about PATH or about which command a shell resolves. It states that terminals run the command by name when `~/.local/bin` is on PATH. Learning PATH would mean running the person's shell startup files, which can read the Keychain, call a password manager or open protected folders, and so show prompts credited to SpaceTerm; SpaceTerm runs no shell for this and edits no shell profile. [The Command Line Tool module](../../src/command_line_tool.rs) owns the row's states and refusals.

Executable and grammar replacement is direct. There is no `spaceterm-server` executable, alias, shim, symlink or old command grammar. [Signing] Developer ID, hardened runtime, notarization, the installer's requirement check and team pinning are future work; none is required for this executable split.

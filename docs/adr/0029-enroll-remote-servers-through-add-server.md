# Enroll remote Machines by invitation

The Machine's own `spaceterm pair` creates the Invitation Link. The desktop's Add Machine and the command line's `spaceterm machine add` consume it with the same outcomes. SSH Setup remains an optional desktop method that installs SpaceTerm Core and enrolls the Machine through OpenSSH. Application-menu, command-palette and operating-system invitation shortcuts open Add Machine. A client joins only a SpaceTerm Core of its own build identity. [The direct connections registry](../../crates/spaceterm-connections/src/worker.rs) refuses any other invitation with `identity_mismatch`, so a Release desktop never pairs with a Preflight Core. [ADR 0056](0056-install-and-pair-servers-from-their-own-command-line.md) owns the Machine's own command-line flow.

The Invitation method offers the same collapsed optional network-address field as SSH Setup. An entered address replaces only the invitation's advertised endpoint, as `machine add --address` does under ADR 0056, and keeps the Machine ID, certificate and proof-key pin. An address that reaches no Machine pauses the join with the existing unreachable message, and one that reaches a different Machine fails verification. Neither changes the pin. Add Machine validates the address before Join and keeps the link for another try. [The direct connections registry](../../crates/spaceterm-connections/src/worker.rs) applies it through the invitation's own address replacement.

`Management::Invite { advertise }` accepts a validated `HOST[:PORT]` as the invitation's advertised authority. It accepts DNS names and IP addresses independently of the listener's bind address and local interfaces, so NAT and cloud public addresses work. `Management::Claims { invitation }` scopes pending-claim reads to a supplied invitation ID. [The direct host](../../crates/spaceterm-core/src/direct/host.rs) validates these management requests; [the direct wire types](../../crates/spaceterm-core/src/direct/wire.rs) define them.

SSH Setup uses [OpenSSH authority](0003-use-openssh-for-server-setup.md) temporarily to discover the approved account installation, offer verified installation when missing, obtain required operating-system consent, explicitly start SpaceTerm Core, configure reachable Network Access and enroll the client. Reversing deliberate Stop requires explicit startup authorization inside setup. Incompatibility leaves the installation intact for administration on the Machine itself.

SSH Setup runs a preflight script right after SSH authentication, before discovery and before any offer or upload. [The preflight reply](../../crates/spaceterm-core/src/provisioning/preflight.rs) is one line that reports the computer's system, architecture, account, macOS or glibc version, systemd user manager, linger, GUI login and FileVault state. Setup refuses the first that applies, in this order: an Intel Mac, ARM Linux, any other system, macOS older than 26.0, glibc older than 2.35, the root account, Linux with no systemd user manager, and a Mac with nobody logged in. The last refusal also reports whether FileVault is on, because automatic login is unavailable then. Each refusal is one [`SetupRefusal`](../../crates/spaceterm-core/src/provisioning.rs), which the desktop shows as one sentence.

Remote Linux requires linger, because a paired device needs SpaceTerm Core to keep running after the SSH user logs out. When the account has no linger, setup asks before upload. It first runs `sudo -n loginctl enable-linger`, then asks for the account password and passes it to `sudo -S` on standard input. Declining refuses with `linger_declined`. [SSH provisioning](../../src/ssh/provisioning.rs) owns these steps.

The SSH destination is sufficient to begin setup. OpenSSH's evaluated HostName supplies the default QUIC hostname; its SSH port remains independent of the QUIC port. A collapsed optional network-address field accepts a DNS name or IP address with an optional QUIC port. DNS names remain in Saved Connections and resolve on each connection. The reachable address and SpaceTerm Core's listening address are separate facts shown in network consent. SSH routing through a jump host does not establish QUIC reachability.

Installation consent binds one signed artifact's identity, target and complete digest; transfer and installation revalidate those bytes. Turning on Network Access requires deliberate authorization for a reachable endpoint. Successful installation or startup alone never completes Add Machine. Success requires persisted pairing credentials and Saved Connection, closed SSH resources and authenticated QUIC admission. Unreachable QUIC or failed credential persistence presents an actionable setup result without publishing an SSH connection. When setup itself turned Network Access on and the enrolled device then reaches no SpaceTerm Core over QUIC, setup keeps its SSH connection open for the cleanup. It cancels the enrollment, restores Network Access as it was and refuses with `udp_blocked`, naming the UDP port. Try Again turns Network Access on again.

One setup attempt owns one foreground SSH authentication connection through discovery and approval waits. Multiplexed commands require that exact owned connection and cannot fall back to fresh authentication. Setup shows its current phase and yields to Authentication Prompts only while interaction is required. The remote-command observation deadline begins after authentication; transfers have no whole-upload deadline. Cancellation releases owned processes and input suppression. Admitted service effects are observed and reported truthfully, without claiming rollback; enrollment cleanup targets only the exact claim and pairing.

After setup, terminal work, directories, status, reconnect, relaunch, Pane Try Again and pairing recovery use QUIC exclusively. [ADR 0057](0057-administer-servers-over-the-service-lane.md) owns remote service administration. Saved Connections retain no SSH runtime route or fallback.

[ADR 0052](0052-carry-paired-connections-over-quic.md) owns the paired transport.

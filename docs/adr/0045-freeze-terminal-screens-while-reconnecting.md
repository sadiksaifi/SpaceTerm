# Freeze terminal screens while reconnecting

When a SpaceTerm Client unexpectedly loses its server connection, it keeps its last displayed terminal screen visibly frozen with "Reconnecting..." and a Retry action. Automatic reconnect uses bounded backoff while terminal input remains disabled. Interrupted input is discarded and never replayed.

Ordinary network loss may continue retrying with backoff. Protocol failures and unconfirmed shell starts instead have a bounded recovery episode that retains the original typed cause across later transport failures and presentation replacement. Sustained successful polling renews automatic recovery. Persistent failure presents its cause and explicit recovery controls rather than indefinite reconnect progress. Retry observes passively; it neither starts a replacement shell nor restarts or updates the server. An unconfirmed shell start remains guarded until the original result or server-run evidence settles it, including across Disconnect and Connect within the client process.

Before enabling input, the client reconciles [authoritative server state](0036-publish-workspace-changes-to-connected-clients.md) and verifies [Pane control](0022-give-one-client-control-of-each-pane.md). Another client's takeover remains effective. A Takeover Screen remains visible throughout the interruption without revealing an older terminal screen, and reconnect never takes over automatically.

Reconnect validates the original server and build identity with the admitting route's authority under [ADR 0027](0027-trust-paired-clients-equally.md). A stable nonsecret Client Identity retains personal views, attachments and eligible control across relaunch; it supplies no connection authorization. Local reconnect uses owning-account authority without native credential access. SSH continuation and restricted original-operation resolution follow [ADR 0029](0029-pair-clients-automatically-during-ssh-bootstrap.md). Direct-network continuation retains paired-device authority and verified server trust. Background continuation defers interactive authentication and provider consent to requested remote work or Connect/Resume.

SSH continuation belongs to one worker for the requested connection intent, and that worker publishes the status the Workspace Window and the Servers section present without another Check Status. Transient transport loss and sleep permit bounded retry backoff; authentication, host, account or server changes pause it. Previously active intent may be restored quietly after client relaunch. BatchMode alone does not prove that an SSH agent or credential provider stays silent, so a restored route that needs fresh authentication waits for Connect/Resume and shows that state. A saved connection keeps whether its intent is active; an inactive one is listed without discovery. Merely saving a host, constructing its row or opening Settings grants no connection intent. Disconnect and deliberate Stop end ordinary retries and keep the connection saved; connection removal ends them and forgets it. Fresh interaction requires requested remote work, Check Status or Connect/Resume and never renews a destructive operation's approval.

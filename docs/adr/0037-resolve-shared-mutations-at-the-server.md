# Resolve shared mutations at the server

The SpaceTerm Server orders and validates shared mutations against its authoritative state before committing and [publishing them](0036-publish-workspace-changes-to-connected-clients.md). An edit identifies the version of the field it changes: when two clients rename the same Workspace from the same version, the first accepted rename succeeds and the second receives a typed conflict. The client preserves the rejected draft and presents the current name for explicit review before retrying; unrelated changes such as Tab creation do not invalidate the rename.

Independent Tab creation requests create distinct Tabs. A mutation targeting a killed Workspace fails without recreating it, and Worktree removal revalidates Git state and the affected terminal work before acting under [ADR 0019](0019-create-and-remove-worktrees-by-running-git.md). Shared state changes do not depend on which client has the affected Tab focused.

Eligible connected interactions present optimistically throughout the client. After required Close Confirmation, a Pane or Tab disappears immediately, without loading, Takeover or reconnect presentation. A bounded ordered pending model preserves distinct rapid actions and dependencies, including a split in a pending new Tab. Pending presentation grants no terminal input authority, fabricates no output, and asserts no confirmed server outcome. Connection establishment and other work with meaningful progress retain their loading presentation.

A definite refusal restores the affected view or draft while preserving unrelated later work. Conflicts require explicit review. The client presents each refusal or failed Worktree operation once, through the surface that asked for it or else its Workspace Window. An outcome counts as presented only when the person responds to the surface showing it: answering its alert, or acting again in the form or Settings that shows it. An outcome on screen but unanswered when SpaceTerm crashes or quits shows once more afterwards, because showing it twice is better than losing it. The client's private journal keeps up to 32 unpresented outcomes across crashes and relaunches, independently of the server's acknowledgement; beyond that it forgets the oldest and the client says once that some earlier results could not be shown. A lost reply remains an unresolved Original Operation; the client resolves that operation before retiring it or dispatching dependent work. Pending connected actions do not become offline mutation queuing under [ADR 0047](0047-keep-workspace-edits-unavailable-offline.md). Reconciliation preserves newer client intent under [ADR 0041](0041-keep-each-clients-view-independent.md), and never renews destructive consent.

Retries carry the original operation identity so the server recognizes the operation and its outcome rather than creating a duplicate Tab or repeating a destructive action. Reconnecting clients reconcile with authoritative server state before retrying an unresolved edit.

The server retains each outcome until its client acknowledges it. It holds at most 32 outcomes and records for 64 client identities. [Revocation](0038-unpair-devices-without-blocking-local-connection-removal.md) forgets the revoked identity's record along with its outcomes, because that identity never connects again. A Worktree write still in progress keeps them until it settles. When the records are full, a new client's first edit replaces the record of the least recently editing client that retains no outcome. A replaced client acknowledged every outcome it had, so the server still accepts its unresolved Original Operation under its original sequence. Its new edits continue above every sequence it used, so it never reuses an operation identity. An unacknowledged outcome of an identity that never returns, such as an account-local client reinstalled under a new identity, stays retained.

[ADR 0050](0050-push-terminal-presentation-over-one-multiplexed-connection.md) resolves a shared edit in one round trip and keeps the server's disk syncs off the request path.

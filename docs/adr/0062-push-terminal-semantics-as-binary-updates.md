# Push terminal semantics as binary updates

Assistive technology reads a Pane's terminal semantics: its rows with their identities, its visible lines, its cursor and its Selection. The server owns row identity and Selection, so a client never derives semantics from screen frames. The client used to pull each revision as one JSON document in 32 KiB chunks and ask again after `Pending`. At 10,000 rows, every cursor move resent the whole row topology, and a resize held 3.8 GiB at its peak. The server now pushes semantics as postcard messages relative to the revision the client acknowledged. They travel on the work connection of [ADR 0050](0050-push-terminal-presentation-over-one-multiplexed-connection.md), over account-local IPC and paired QUIC alike under [ADR 0028](0028-use-spaceterm-protocol-over-every-client-connection.md).

A client starts demand for a channel with the `AccessibilityDemand` operation when assistive technology first reads that Pane. Demand is never gated on detecting VoiceOver or on a timeout. Each start names a demand generation greater than every earlier start on that channel. Demand ends when the client ends it, releases or closes the channel, or loses the connection. While demand stands, the server keeps a semantic store for the channel: the models of the acknowledged revision and of the revision in flight. Ending demand drops the store. An observation channel's demand and acknowledgements are refused under [ADR 0059](0059-observe-panes-without-taking-control.md).

Each revision is one or more consecutive messages on its channel. Every message names the demand generation, the revision and its base, which is the acknowledged revision of the same generation it applies to, or none for a complete document. A revision carries topology splices first, then the rows that are new or changed since the base, then a tail. A splice removes rows at a line and inserts runs of consecutive page rows from one page node. A row carries its line, revision, soft-wrap flag and text. It carries cell spans of column, width and byte length only when it is not one column per character. The tail carries the visible lines, the cursor and the Selection as lines and columns of the revision's topology. A revision that changes only the cursor, the Selection or the visible lines is a tail alone, under 256 bytes at any row count. A complete document of 10,000 rows of 80 ASCII characters is under 1.2 MB.

No message exceeds 32 KiB, so a semantic message never continues across frames. A splice that does not fit continues as splices that remove nothing. A row that does not fit continues as fragments of whole cells, which can cross messages. Semantic text is lossless: a cell keeps its whole grapheme, up to the base codepoint and 64 suffix codepoints the Terminal Emulator stores, and a row holds up to 512 such cells. The visual limit on cell text in screen frames does not apply to semantics. A message that breaks a bound is a protocol violation.

A revision's topology holds at most 65,536 rows, and its messages carry at most 128 MiB. A client refuses a revision past either bound as a protocol violation, so a faulty or remote server cannot make it queue, stage or retain unbounded semantic state. The bounds are twice what a server's document can reach. Its topology holds the 10,000-row Scrollback cap, at most one more history page, because the Terminal Emulator trims Scrollback a whole page at a time, and at most 256 screen rows. A page holds about 15,500 rows at the narrowest Pane. Its text and spans take about as many bytes as the 50 MB of pages the Terminal Emulator keeps for Scrollback.

Semantic updates follow the frame pattern of ADR 0050. Each channel has one semantic credit, separate from its frame credit, so at most one revision is unacknowledged. The client acknowledges a revision with `AccessibilityAck`, naming its demand generation, after it applies the tail. The client stages a revision's messages and applies them only at the tail, so assistive technology never reads part of a revision. It stages a delta only when its base equals the revision it applied last in the same generation. A newer model replaces one the server has not started to encode. The connection's I/O thread encodes from the captured models outside the server lock, one message per L1 turn, so frames, replies and other Panes interleave with a large revision. It starts no thread per revision and keeps no encoded document after writing it. The client never polls, because updates arrive for as long as demand stands. The update itself announces a new revision, so no Pane event does. The JSON encoding and the accessibility `Chunk` reply are gone.

Semantic work never publishes a screen. Building or continuing a semantic model never flushes a frame ahead of the pacing deadline in ADR 0050, so demanding semantics adds no frames during continued output. Each frame still carries the semantic revision current at its capture. The client binds the document it applied last to the frame it presents last, and binds it again to each later frame. It never waits for a frame that carries a particular semantic revision, because frame coalescing can skip that revision and an idle Pane sends no further frames.

A demand generation fences one demand from the next. The client discards every message of an earlier generation without acknowledging it, and stages nothing of a new generation until its complete document begins. The server forgets the in-flight revision and the acknowledged base when demand starts, and revisions increase within a generation only, so a new generation can resend a revision number. An acknowledgement of an earlier generation is ignored and returns no credit. Within the current generation, an acknowledgement of a revision that is not in flight is ignored without credit when it is at or below the highest revision whose tail the server wrote in that generation, and is a protocol violation otherwise. An acknowledgement of a later generation than the channel's last start is a protocol violation. An acknowledgement on a channel that has closed is ignored, so it never ends the connection's other Panes.

A hidden channel receives no semantic updates, as it receives no frames. Demand and the store persist while the channel is hidden, and the Terminal Session does no semantic work while no visible channel requests it. The client keeps its document across hide. Hide suspends a revision whose messages have started: the server keeps its captured model, its position and its credit, and the client keeps what it staged. On show, the server sends the rest of that revision through its tail, then, after its acknowledgement, one revision of the latest model against it. A revision not yet started is replaced on show by one against the acknowledged base, so showing a Pane resends only what changed. Ending demand, Release, Close, the end of the Terminal Session and the end of the connection abort an unfinished revision: the client discards what it staged, the server releases the store without waiting for credit, and no event on the channel waits for a semantic acknowledgement.

A new connection starts without a store. After the client claims the Pane again, it starts demand, and the first update is a complete document. The client resolves Selection only against a document it received on the current connection. A Selection made through assistive technology still travels as the `AccessibilitySelection` operation, which names row identities and revisions, and the server applies it.

Both processes retain each row's text once. They derive cell references on demand from the row identity, row revision and column. A UTF-16 index exists only for a row with non-ASCII text. Retained rows stay under 3 MiB per 10,000 rows of 80 ASCII characters in each process.

[The wire types](../../crates/spaceterm-server/src/pane/accessibility.rs) own the message layout, its bounds and how a revision is split into messages.

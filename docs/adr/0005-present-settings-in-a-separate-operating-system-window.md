# Present Settings in a separate Operating-System Window

SpaceTerm presents Settings in its own modeless Operating-System Window rather than as a panel, tab, or modal inside a Workspace. Settings is application scoped: it edits one retained document that governs every window, it must stay reachable when no Workspace window exists, and a person adjusting a terminal font needs to watch a live terminal while doing it. A Workspace-owned panel would tie an application-scoped document to one Workspace's lifetime, would have to be reopened per Workspace, and would cover the very output being configured. A modal would forbid exactly the interleaving that makes appearance settings usable.

The window is deliberately ordinary. The host selects the ordinary window kind: Floating on macOS and Normal on Linux, where Floating instead creates a transient parent relationship. It stays movable, and tabbing, resizing, and minimizing are withheld so it behaves as one stable settings surface rather than a document window. It is rendered entirely in GPUI with no host settings control. Its navigation list, search field, and scrolling detail pane remain product policy in `src/ui`; the host supplies window capabilities and application commands. Linux client decorations follow desktop button choices while keeping the controls together at the trailing edge.

A Settings window is not a Workspace window. Every decision about whether a Workspace still exists resolves through the Workspace windows in GPUI's registry rather than the raw window count, so an open Settings window cannot suppress reopen, `New Workspace`, or default-window restoration, and cannot be asked to confirm an application quit it has no work to hold.

Editing applies instantly. Each change previews live through the existing preview transaction and commits shortly after the last change, and while the window is closing any change that has not settled is written synchronously because an asynchronous write would be cancelled with the window that owns its task. This is why the Settings surface has no save or cancel action and needs no unsaved-change confirmation: there is no uncommitted state to lose. The consequence is that a failed or unverifiable write is a reported condition rather than a discarded edit — a failure keeps the change previewing and offers a retry, and a document that cannot be read or whose identity cannot be verified pauses editing until an explicit reload, so SpaceTerm never replaces content this session never saw.

A person who wants to edit the Settings Document as text edits `settings.json` in their own editor rather than inside SpaceTerm. The Advanced section shows the file read-only with its location, and Edit JSON opens it in the program the Operating System assigns to it, writing any pending change first and writing the document if no file exists yet. A text editor inside SpaceTerm would need its own Apply and Cancel, because a half-typed document is not a setting; the person's editor already saves whole files. SpaceTerm watches the file's directory and adopts every save it did not make the way an explicit reload adopts it. Reload in the same section reads the file on request, for a save the watch did not report; it writes any change the window can still write first, so it discards only a change that the file already superseded. A valid save reaches every window. A malformed or unsafe save keeps the last valid settings and pauses editing until a valid save arrives. A save that lands while the Settings Window has its own change outstanding waits for that change's write, which then finds the file changed and pauses editing until the person reloads, so the conflict is reported rather than resolved silently.

The Settings surface owns the authoritative draft rather than reading the transaction back, because the settings owner refuses a preview update while a commit is in flight and retires a preview token once the committed revision moves. Without a draft, a change made inside either window would be silently dropped.

Per-role color override editing is deliberately absent. The document supports overrides across the Terminal color roles, and they remain reachable through the settings file, but presenting them needs a color-picker control and a role taxonomy that this surface does not yet have. Theme selection, the installed-theme catalog, the Zed extension registry, Zed family import, removal, and reset cover the Terminal Theme capability without it.

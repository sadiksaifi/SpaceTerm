# Restart SpaceTerm Core into its Pending Version and return on failure

Updating SpaceTerm Core takes two steps. [ADR 0040](0040-install-core-versions-from-the-feed-a-push-or-a-local-archive.md) owns the first: installing a Pending Version beside the running version, which ends nothing. This record owns the second: the restart that moves SpaceTerm Core to the Pending Version and ends that Machine's Terminal Sessions.

Client and SpaceTerm Core release numbers may differ. Work admission requires a shared protocol major under [ADR 0035](0035-negotiate-protocol-versions-per-connection.md). Refusal leaves other connections and Core-owned work intact. Client updates restart the client and preserve Core-owned work.

## When SpaceTerm Core restarts

A restart is silent only when no Terminal Session is live, and only into a Pending Version that is not breaking. A Pending Version is breaking when its work or service protocol major differs from the running Core's. A breaking restart always asks, and its confirmation names the Paired Devices that cannot connect until they update. [The update engine](../../crates/spaceterm-core/src/service/runtime/updates.rs) follows the live Terminal Session count once the server is ready and admits a silent restart at zero sessions. It tries each Pending Version silently at most once per boot, so a start that fails does not loop. A restart into a Stepping Stone of [ADR 0064](0064-step-updates-through-update-floors-and-migrate-data-generations.md) follows the same rule, and the update check that follows it may restart again under it. At boot the service manager starts the approved version first. With no session live, the engine then restarts it into a waiting Pending Version.

Any paired device may ask for a restart over the [service lane](0057-administer-servers-over-the-service-lane.md). Restart moves into the Pending Version when one waits, and into the running version otherwise. Its confirmation names the Machine, the running version, the Pending Version and the Terminal Sessions that end. A changed installation, SpaceTerm Core boot, deliberate Stop state or affected Terminal Session set requires fresh confirmation. Identity, pairings and [Workspace organization](0031-retain-workspace-organization-across-server-restarts.md) survive; retained Panes follow [ADR 0043](0043-start-restored-shells-on-first-use.md). Restarting a stopped SpaceTerm Core into its Pending Version leaves it stopped.

## How the restart runs

A helper from the running runtime performs every restart into a Pending Version, outside the server it replaces, under [ADR 0057](0057-administer-servers-over-the-service-lane.md). [The activation](../../crates/spaceterm-core/src/service/activation.rs) stops the server, waits for its cleanup and copies the retained state, `identity.json` and `direct.json`, beside itself. It then points the service registration at the Pending Version and starts it. The Pending Version marks itself ready durably before it publishes its endpoint. A Pending Version that is not ready within the readiness deadline of 60 seconds after its Start, or whose Start fails, is stopped. The activation then restores the retained-state snapshot, points the registration back at the previous version and starts it. A Pending Version that cannot migrate the Core's Data Generation never becomes ready, so it returns the same way, and the previous version restores the migration backup under ADR 0064.

The [update record](../../crates/spaceterm-core/src/service/runtime/updates.rs) names how a restart ended, and every client reads it in the update facts as `last_failure`. A version that did not become ready is skipped: SpaceTerm Core refuses it from every source until a newer one appears. A full disk, or a Network Access port that another program holds, says nothing about the version. Those failures keep it as the Pending Version, and the next restart tries it again. Ended Terminal Sessions never return. No manual return exists.

## Recovery

Every activation step is durable before its native call, and recovery never repeats a destructive Stop or a candidate's Start. An admitted restart survives the client that asked for it. A power loss can interrupt an activation after the registration names a Pending Version that may never start. From that replacement until the Pending Version is ready or the return finished, a boot entry runs the previous runtime's recovery helper: a systemd user oneshot unit on Linux and a LaunchAgent on macOS. A Core that boots into an activation it may not run also launches that helper from the previous installation. The helper finishes the activation by starting the Pending Version or by returning to the previous one. The update engine applies the outcome the activation journal proves to the update record before it reports any fact, so a lost helper leaves no stale Pending Version. Uncertain outcomes refuse terminal admission.

Every service operation holds the account's service lock, including Start, Stop, Restart, Uninstall and changes to automatic startup. A desktop launch that finds the lock held waits for the operation to end instead of failing. After one second, the launch screen says another SpaceTerm Core operation is running. That screen offers no action and opens the Workspaces once the operation ends. A local client admission during a Restart also waits, so Panes reconnect on their own. Each wait wakes when the operation ends and gives up after three minutes. A launch that reaches that limit says SpaceTerm Core is busy and offers Try Again. A closed window or Pane ends its wait. SSH Setup waits at most one second, so it answers within the desktop's observation.

[ADR 0052](0052-carry-paired-connections-over-quic.md) owns the paired transport.

# Start restored shells on first use

After SpaceTerm Core restarts, it immediately restores its saved [Workspace organization](0031-retain-workspace-organization-across-server-restarts.md). Each retained Pane starts a fresh shell when a client first selects it and holds control under [ADR 0022](0022-give-one-client-control-of-each-pane.md). Opening a Tab or Workspace the person chose applies this rule to that client's Focused Pane. Two moments count as that choice. The person's own launch of the desktop opens its Active Workspace's Active Tab and starts that Focused Pane, or creates one Local Workspace and opens its Root Pane when nothing is attached; Workspaces the person detached stay detached. That landing waits while a retained copy stands in for the Core or the Core can't yet take a creation, then happens once; a creation the person asks for meanwhile replaces it. That launch first opens the Workspace, Tab and Focused Pane the client last presented from this computer after a Pane there was explicitly selected, by the person or by this landing, which [its client view store](../../crates/spaceterm-core/src/client_view.rs) retains, while the Core's inventory and the client's attachments still present that Workspace. A Tab or Pane that is gone leaves the Root Tab or Root Pane, a missing or unreadable selection leaves the default, and input the person gives the window before this computer's Workspaces arrive keeps the saved selection from moving the view or the keyboard. A passive launch's default replaces no saved selection. When SpaceTerm Core restarts while a client presents a Pane whose live Session it showed, and that Pane is the Focused Pane of the Tab and Workspace the person has open, its fresh shell starts as soon as the client sees the restarted Core.

Every other retained Pane of the client's attached Workspaces then starts in the background, so it is ready when the person opens it. [The window's preparation queue](../../src/ui/terminal_readiness.rs) bounds how many start at once, each from its turn until the shell it started reports a prompt or a name of its own, fails or has had five seconds, also when the start's reply was lost, and ranks visible Panes, the Tabs next to the one in use and recently used Tabs first. A background start grants no control to any client under [ADR 0022](0022-give-one-client-control-of-each-pane.md) and moves no focus; selecting the Pane later acquires it. [SpaceTerm Core](../../src/runtime/core_host/workspaces.rs) starts each Pane once per run through `AttachmentClaim::Prepare`, which work 1.4 adds; a client sends it only to a Core whose admission selected that minor. A Pane another client created, a Pane whose Session ended in the running Core, a start whose outcome is unconfirmed and an unavailable directory never start this way, and closing a Pane before its turn starts nothing. Because Core starts each Pane in the background at most once per run, any observation of that Pane in the same run settles a background start whose reply was lost, whoever controls the Pane by then. A Pane whose worker stopped reconnecting, as one can while its Core is replaced, is asked to connect again once per Core run, so it still waits for its turn. A shell that starts keeps its Pane blank until its prompt arrives. Its Tab and Pane Caption say its whole name at once, instead of saying Terminal first: where it starts, which is the directory SpaceTerm Core confirmed for its Pane or otherwise the Pane's Starting Directory, and the shell predicted for it, which is the shell it reported or otherwise the shell its Machine's other Panes run. They draw that shell quietly until the shell names itself, so nothing moves when it does. With no shell to predict they say only where it starts, and with no directory either they show no words. A Tab follows its Focused Pane at once, so a Split names its Tab for the new Pane on that action. A Pane growing into the layout lays its caption out for the width it reaches. [The Tab view](../../src/ui/tab_view.rs) owns these rules. A Workspace that becomes the Active Workspace only because the person killed or detached the one in use takes the keyboard without selecting a Pane, so none of its Panes acquires control by that change.

The first Controlling Client supplies the initial terminal dimensions. SpaceTerm Core coordinates control acquisition and startup so concurrent clients cannot create duplicate Terminal Sessions for the same Pane. The previous running programs and in-memory terminal state ended with the previous SpaceTerm Core run under [ADR 0030](0030-start-servers-at-boot-independently-of-clients.md).

[ADR 0044](0044-restore-panes-in-their-last-confirmed-directory.md) defines directory selection and recovery for restored shells.

First use does not apply to a Pane whose Terminal Session ended in the running SpaceTerm Core. That Pane waits for Start Session under [ADR 0053](0053-keep-a-pane-whose-shell-exits-unsuccessfully.md).

Reconnecting to a running SpaceTerm Core reuses its existing Terminal Sessions. Once a restored shell starts, it has the independent Core-owned lifetime in [ADR 0030](0030-start-servers-at-boot-independently-of-clients.md).

After a lost shell-start acknowledgement, a fully reopened client first observes the authenticated Machine's existing Pane and Terminal Session state. An unresolved original start permits no replacement start, including through Take Over. [ADR 0037](0037-resolve-shared-mutations-at-the-server.md) owns operation uncertainty; reconnecting or replacing a presentation does not settle it.

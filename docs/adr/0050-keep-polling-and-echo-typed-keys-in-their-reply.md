# Keep polling and echo typed keys in their reply

SpaceTerm Clients keep discovering terminal output by polling each Pane. Following [issue #666](https://github.com/sadiksaifi/SpaceTerm/issues/666), polling stays the baseline, with three changes that remove sequential round trips. One output check per cycle carries the Pane's presentation, native effects and reading completion. An accepted key batch's reply can carry the Pane's next screen. One connection carries many exchanges at once, and each reply returns to its own caller.

An accepted key batch waits on the server for the Pane's next publication. The wait is at most 25 ms: one 16.667 ms presentation frame plus one 8 ms accumulation interval for the shell to echo, rounded up. The reply then carries that screen exactly as the next output check would have, from the same per-Pane encoder, so a later check neither repeats nor skips it. A refused, hidden or no longer controlled batch is answered at once. Without a publication by the deadline, the reply only accepts the batch and the next output check delivers the screen. The wait observes publications without consuming them and never holds the service lock. Only the same device, connection, lease and focus generation can complete the reply, once. Every other completion only accepts the batch, so a lost or late echo never becomes an error or a replay.

Every terminal frame on account-local IPC and paired WSS carries a request ID, which its reply repeats. Admission stays untagged. A desktop keeps one transport per server. Its callers write requests in turn and do not wait for earlier replies before writing. Queued and outstanding requests together stay within twice the Pane limit. The server applies requests strictly in arrival order. Only replies may complete out of order, so a slow reply never delays a faster one. Each caller has one exchange outstanding, so its own requests stay ordered.

A deferred reply waits on its own short-lived thread for that connection, so waits on different Panes do not queue behind each other's deadlines. It then retakes the service lock, repeats the stopping and paired-authorization checks, and completes. Each connection allows 16 deferred replies. Past that, the server completes a reply at once, as if its wait had expired, so reading requests never blocks. A deferred reply that cannot be delivered closes the connection. Outstanding deferred replies end with the connection.

Any read, write or reply failure fences the transport. Requests written without a reply fail as unconfirmed, unsent requests fail as not running, and nothing is replayed. [ADR 0045](0045-freeze-terminal-screens-while-reconnecting.md) continues to govern the frozen screen, recovery and discarded input. Cancellation, [Pane control](0022-give-one-client-control-of-each-pane.md), revocation and reconnection behave as before.

## Considered options

- **Server push of screen changes.** The server would send each Pane's changes as it publishes them. This was rejected for issue #666. It replaces the polling model and its reconnect, control and backpressure behavior across both clients for a gain the key echo already provides where latency is visible: typing.
- **One connection per Pane.** This would exceed the direct connection limit at the Pane limit and repeat TLS, admission and capability setup for every Pane.

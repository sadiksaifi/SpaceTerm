# Push terminal semantics as binary updates

Assistive technology reads a Pane's terminal semantics: its rows with their identities, its visible lines, its cursor and its Selection. The server owns row identity and Selection, so a client never derives semantics from screen frames. The client used to pull each revision as one JSON document in 32 KiB chunks and ask again after `Pending`. At 10,000 rows, every cursor move resent the whole row topology, and a resize held 3.8 GiB at its peak. The server now pushes semantics as postcard messages relative to the revision the client acknowledged. They travel on the work connection of [ADR 0050](0050-push-terminal-presentation-over-one-multiplexed-connection.md), over account-local IPC and paired QUIC alike under [ADR 0028](0028-use-spaceterm-protocol-over-every-client-connection.md).

A client starts demand for a channel with the `AccessibilityDemand` operation when assistive technology first reads that Pane. Demand is never gated on detecting VoiceOver or on a timeout. It ends when the client ends it, releases or closes the channel, or loses the connection. While demand stands, the server keeps a semantic store for the channel: the models of the acknowledged revision and of the revision in flight. Ending demand drops the store. An observation channel's demand is refused under [ADR 0059](0059-observe-panes-without-taking-control.md).

Each revision is one or more consecutive messages on its channel. Every message names the revision and its base, which is the acknowledged revision it applies to, or none for a complete document. A revision carries topology splices first, then the rows that are new or changed since the base, then a tail. A splice removes rows at a line and inserts runs of consecutive page rows from one page node. A row carries its line, revision, soft-wrap flag and text. It carries cell spans of column, width and byte length only when it is not one column per character. The tail carries the visible lines, the cursor and the Selection as lines and columns of the revision's topology. A revision that changes only the cursor, the Selection or the visible lines is a tail alone, under 256 bytes at any row count. A complete document of 10,000 rows of 80 ASCII characters is under 1.2 MB.

The server fills each message to about 32 KiB. The item that does not fit starts the revision's next message. A row larger than that travels alone, and no message exceeds 64 KiB, so a semantic message never continues across frames. A message that breaks a bound is a protocol violation.

Semantic updates follow the frame pattern of ADR 0050. Each channel has one semantic credit, separate from its frame credit, so at most one revision is unacknowledged. The client acknowledges a revision with `AccessibilityAck` after it applies the tail. A newer model replaces one the server has not started to encode. The connection's I/O thread encodes from the captured models outside the server lock, one message per L1 turn, so frames, replies and other Panes interleave with a large revision. It starts no thread per revision and keeps no encoded document after writing it. The client never polls, because updates arrive for as long as demand stands. Each frame still carries the semantic revision current at its capture, so the client binds a semantic model to the frame that shows it. The update itself announces a new revision, so no Pane event does. The JSON encoding and the accessibility `Chunk` reply are gone.

An acknowledgement of a revision that is not in flight is ignored when the server sent that revision earlier on the channel. Any other such acknowledgement is a protocol violation. Each demand start begins without a base, so its first update is a complete document. After a start, the client discards every update until it applies a complete one, so a message written before the start never reaches its document.

A hidden channel receives no semantic updates, as it receives no frames. Demand and the store persist while the channel is hidden, and the Terminal Session does no semantic work while no visible channel requests it. The client keeps its document across hide. On show, the server sends one revision against the acknowledged base, so showing a Pane resends only what changed.

A new connection starts without a store. After the client claims the Pane again, it starts demand, and the first update is a complete document. The client resolves Selection only against a document it received on the current connection. A Selection made through assistive technology still travels as the `AccessibilitySelection` operation, which names row identities and revisions, and the server applies it.

Both processes retain each row's text once. They derive cell references on demand from the row identity, row revision and column. A UTF-16 index exists only for a row with non-ASCII text. Retained rows stay under 3 MiB per 10,000 rows of 80 ASCII characters in each process.

[The wire types](../../crates/spaceterm-server/src/pane/accessibility.rs) own the message layout, its bounds and how a revision is split into messages.

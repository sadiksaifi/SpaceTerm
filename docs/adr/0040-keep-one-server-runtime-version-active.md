# Keep one server runtime version active

Each operating-system account and application identity has one active SpaceTerm Server runtime version under [ADR 0033](0033-reuse-one-server-across-headless-and-desktop-installations.md). Existing clients, newly connected clients, and newly created Workspaces all use that running version, so server ownership and capabilities do not split by release version.

Signed server candidates may be verified and staged alongside the approved installation without becoming active. Client launches, reconnects, Workspace creation, and protocol incompatibility do not activate a staged candidate or launch a second server. Settings distinguishes the approved or running server version from the candidate included with that client.

Activation requires the explicit server-update confirmation in [ADR 0034](0034-confirm-server-update-restarts-and-explain-incompatibility.md) and replaces the running version after ending its Terminal Sessions. Boot, crash recovery, and Start Server select the durably approved installation rather than the newest staged release. Updating a deliberately stopped server leaves it stopped under [ADR 0030](0030-start-servers-at-boot-independently-of-clients.md).

Client installation and update lifecycles preserve the approved server's executable and resources independently of the client installation. Service registration resolves that server installation even when a different desktop or headless installation discovers it.

Desktop candidate preparation embeds an explicitly selected, independently signed server archive and signature and pins the complete archive digest into the client executable. Several client releases may reuse the same byte-identical archive, including its executable, resources and build metadata. Matching client and server release numbers are unnecessary. An identical approved artifact needs no server update.

Candidate verification checks signature, complete archive digest, application identity, native target, resources and declared compatibility before activation is offered. A running client whose installation now contains another candidate must restart before using it. Installed Preflight verifies Server Candidates against the separate nonproduction trust in [server-nonproduction-trust.json](../../packaging/server-nonproduction-trust.json). Its signing seed is deliberately public and grants no Release authority. Release accepts only its production trust and rejects nonproduction signatures. Both retain the same identity, target, digest, resource and compatibility checks. Candidate preparation owns signing; launch never signs an artifact or promotes a sibling executable into an approved service runtime. Previously retained Preflight and Development runtimes signed under production trust remain authenticated for Start, recovery and the previous side of an explicit update. New candidate admission requires the receiving identity's current trust; this compatibility rule neither activates another runtime nor changes retained state.

The foreground source Development workflow in [ADR 0030](0030-start-servers-at-boot-independently-of-clients.md) runs the current source without staging or approving a distribution artifact. It does not replace the approved service runtime. [The local workflow](../local-server.md) describes both workflows.

Staging and activation on an SSH account server use that account's own operating-system authority over the route that admitted its connection, without a SpaceTerm paired-device credential. The client transfers only an artifact it verified for that machine's application identity and native target, and the account retains and activates only that exact artifact.

An admitted activation retains its exact candidate and original observations durably, separately from deliberate Stop. Ordinary service, desktop and control entry points recover that operation under [ADR 0034](0034-confirm-server-update-restarts-and-explain-incompatibility.md). SSH update preparation, admission and recovery use the same verified candidate's maintenance code so an older approved runtime need not understand new nonproduction trust. Recovery never chooses an arbitrary staged artifact. No permanent update helper is installed.

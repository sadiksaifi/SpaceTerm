# Confirm server updates and explain incompatibility

Client and server release numbers may differ. Work admission requires the [supported protocol major and required capabilities](0035-negotiate-one-protocol-major.md). Refusal distinguishes an unsupported major from a missing capability and leaves other connections and server work intact. Explain which side needs updating only when verified information establishes the direction.

Client updates restart the client and preserve server-owned work. A server update stages a verified candidate and activates it after confirmation. The candidate comes from the client's own catalog on the same machine, from the server's fetch of its target's signed release asset, or from a paired client's upload. The server verifies it before staging. Confirmation binds the server's own observations. Settings, status controls and local incompatibility recovery open the account-local Update Server journey when a verified different candidate is available. The CLI offers remote Update Server over the [service lane](0057-administer-servers-over-the-service-lane.md).

Confirmation names the server, its current version and the exact candidate. It states that every client's Terminal Sessions on a running server end, or that a server that isn't running ends none. Changed installation, server boot, deliberate Stop state or affected Terminal Session set requires fresh confirmation. Identity, pairings and [Workspace organization](0031-retain-workspace-organization-across-server-restarts.md) survive; retained Panes follow [ADR 0043](0043-start-restored-shells-on-first-use.md). Updating a stopped server leaves it stopped.

Admitted operations survive the initiating client or Settings Window. Recovery resolves the original exact-target operation without repeating destructive dispatch or choosing another candidate. Uncertain outcomes refuse terminal admission. [ADR 0057](0057-administer-servers-over-the-service-lane.md) owns CLI activation recovery and passive checks. When return is eligible, [`spaceterm server update`](../../crates/spaceterm-cli/src/server/update.rs) offers return to the previous verified runtime before staging a candidate. This applies to both running and offline servers. Return requires proof that the candidate never became ready and saved state is unchanged. Ended Terminal Sessions never return. A verified native candidate may use a different protocol major; work admission still requires a shared major, while the service lane remains available to resolve the update. [ADR 0040](0040-keep-one-server-runtime-version-active.md) owns runtime activation.

Every service operation holds the account's service lock, including Start, Stop, Restart, Update, Uninstall and changes to automatic startup. A desktop launch that finds the lock held waits for the operation to end instead of failing. After one second, the launch screen says another server operation is running. That screen offers no action and opens the Workspaces once the operation ends. A local client admission during a Restart or Update also waits, so Panes reconnect on their own. Each wait wakes when the operation ends and gives up after three minutes, which exceeds a slow Linux stop with its cleanup and startup. A launch that reaches that limit says the server is busy and offers Try Again. A closed window or Pane ends its wait. Server setup through SSH waits at most one second, so it answers within the desktop's observation.

[ADR 0052](0052-carry-paired-connections-over-quic.md) owns the paired transport.

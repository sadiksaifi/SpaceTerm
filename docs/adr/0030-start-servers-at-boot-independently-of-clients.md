# Run SpaceTerm Core independently of clients

Installed Preflight and Release run SpaceTerm Core through the owning nonroot account's host service manager. Normal desktop launch provisions an exact verified independent runtime only when service policy is absent, then presents Core-owned local work. Client exits, crashes, and disconnections leave Core-owned terminal work running.

On macOS, an account LaunchAgent runs in `gui/<uid>` with `LimitLoadToSessionType=Aqua`. It starts at graphical login and stops at logout. SpaceTerm Core on a Mac requires a logged-in GUI session; `setup` without one fails with `unsupported_session`, and SSH Setup refuses before upload with `nobody_logged_in` under [ADR 0029](0029-enroll-remote-servers-through-add-server.md). Installation requires no administrator password.

On Linux, a systemd user service runs SpaceTerm Core. With linger enabled, it starts at boot and survives logout. Without linger, it runs while the person is logged in and stops at logout. That suffices for a Core that only the same computer's desktop and CLI use. Paired devices need linger. `pair` refuses with `linger_required` before it checks Network Access, and turning Network Access on from the computer itself does the same. `spaceterm setup` asks for linger in a terminal; declining it, or running without a terminal, skips the step unless setup also turns Network Access on. SSH Setup on a remote Linux machine requires linger before upload under ADR 0029. Enabling linger requires one scoped administrator authorization through CLI sudo, desktop pkexec or SSH Setup's sudo prompt. [The Linux service](../../crates/spaceterm-core/src/service/linux.rs) reports boot startup only with linger.

No root process executes SpaceTerm code. SpaceTerm Core may live in account application data. Its state uses account-private directories with mode `0700` and files with mode `0600`; these modes restrict other accounts, not processes running as the owning account.

Computer reboot and power loss end live Terminal Sessions and their in-memory terminal state. Automatic startup follows the platform's login or boot policy and the retained Stop Core state. A restarted SpaceTerm Core uses its durably retained nonsecret identity and route-specific admission authority; it does not resume the previous running programs.

[ADR 0043](0043-start-restored-shells-on-first-use.md) defines when retained Panes start fresh shells after SpaceTerm Core restarts.

Start automatically is a retained host-service policy, independent of service installation and deliberate Stop Core state. Changing it does not stop a running SpaceTerm Core, start a stopped one or uninstall the service. It controls login startup on macOS and boot startup on Linux. Only administration on the Machine itself may change it, including `spaceterm setup --automatic-start on|off`. A fresh installation defaults to on. Re-running setup preserves the preference unless the flag is given.

Stop Core stops the SpaceTerm Core service, durably suspends automatic startup, and ends the Machine's Terminal Sessions. SpaceTerm Core stays stopped across client launches, reconnect attempts, and computer reboots until an explicit Start Core action starts it. Start alone reverses deliberate Stop; setup preserves it. Start and Stop preserve the person's automatic-start preference. Service supervision respects deliberate Stop even when that preference is on. Stop, Restart and Uninstall confirmations name the Terminal Sessions that end and state whether Workspaces are kept. Account-wide lingering is outside the Uninstall confirmation.

Start, Stop, Restart, Uninstall and updates use the owning account's service manager. A paired client may Restart or Update a running SpaceTerm Core over its paired connection. SpaceTerm Core records the admitted request, and a transient helper from the approved runtime performs the same account-local operation outside the service's process tree under [ADR 0057](0057-administer-servers-over-the-service-lane.md). Start, Stop and setup run only on the Machine itself, because a stopped SpaceTerm Core accepts no connection and a stopped remote Core could not be started again. The lane refuses a paired Stop with `local_only`. A stopped SpaceTerm Core reports Stopped to its local clients.

Remove Machine uninstalls SpaceTerm Core from a paired Machine and unpairs it in one step. The desktop sends one service-lane Uninstall, which requires `Capability::Uninstall`. [The helper](../../crates/spaceterm-core/src/service/helper.rs) stops SpaceTerm Core, forgets its direct record, which revokes every pairing, and removes the service, the launcher and every installed version. Workspace organization and Machine Settings stay on that computer. Local uninstallation runs on the Machine itself under [ADR 0054](0054-use-one-headless-executable.md). `spaceterm setup` installs, authorizes and starts the service under [ADR 0056](0056-install-and-pair-servers-from-their-own-command-line.md). Local admission and service use require no client credential store; terminal programs retain their normal credential and agent access.

[ADR 0048](0048-end-all-sessions-from-the-selected-servers-settings.md) defines End All Sessions while SpaceTerm Core remains running.

Source Development uses a separate foreground SpaceTerm Core built with its client from the current source, including uncommitted edits. The development command owns both processes and ends their Terminal Sessions when the run ends, including interruption. It requires neither a signed distribution artifact, production credentials nor service registration. It retains Development Settings and Workspace organization between runs. Ownership checks prevent a run from adopting or stopping an unrelated SpaceTerm Core; existing service state and deliberate Stop remain unchanged. This exception changes process lifetime, not Core-owned Workspaces or connection authority.

[ADR 0052](0052-carry-paired-connections-over-quic.md) owns the paired transport.

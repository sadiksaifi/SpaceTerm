# Install SpaceTerm Core versions from the feed, a push or a local archive

Each operating-system account and build identity runs one SpaceTerm Core version and keeps at most one Pending Version beside it. Installing a Pending Version verifies a signed archive and unpacks it beside the running version. It ends no Terminal Session and changes no client. [ADR 0034](0034-confirm-server-update-restarts-and-explain-incompatibility.md) owns the restart that moves SpaceTerm Core to the Pending Version. [ADR 0033](0033-reuse-one-server-across-headless-and-desktop-installations.md) owns shared discovery.

A Release SpaceTerm Core checks its own signed feed two minutes after it starts, every six hours after that, and when a client asks. It installs the release the feed names when that release is newer. Preflight and Development never fetch a feed, so their update check reads `disabled`. They take only a desktop push or a local archive.

A desktop pushes its embedded SpaceTerm Core build to any connected Machine whose platform it embeds, over that Machine's [service lane](0057-administer-servers-over-the-service-lane.md). The desktop verifies each embedded archive once and offers it only to a Core that would install it. `spaceterm update --archive FILE --signature FILE` pushes a local archive the same way. While SpaceTerm Core on this machine is stopped, the CLI installs the archive directly. On Linux, `install.sh` installs a downloaded archive.

Every source follows one version order. SpaceTerm Core refuses a version that is not newer than the version it runs and its Pending Version. It also refuses the version it skipped after a failed start, until a newer one appears. Release versions order by `MAJOR.MINOR.PATCH`. Preflight and Development versions name a commit and have no order, so among them only an installed version is refused. It also refuses a release whose Update Floor is above the version it runs, and the feed reaches that floor first through Stepping Stones under [ADR 0064](0064-step-updates-through-update-floors-and-migrate-data-generations.md). A source asks before it downloads or receives any byte, so a refused version costs nothing. [ordering.rs](../../crates/spaceterm-core/src/update/ordering.rs) owns the rule.

The feed follows the shared schema in [feed.rs](../../crates/spaceterm-core/src/update/feed.rs). SpaceTerm Core verifies the feed's raw 64-byte Ed25519 signature before it reads any field, then checks every field rule. It refuses a release whose `minimum_system` is newer than the host's macOS version or glibc version. It downloads at most the archive size the feed names and checks the size and SHA-256. The update engine then verifies the archive's signature and its build document before it keeps anything.

A Release SpaceTerm Core verifies feeds and archives under the `current` or the `backup` key of [update-trust.json](../../packaging/update-trust.json), which it embeds, and under no other key. Preflight and Development verify pushes and local archives under [core-nonproduction-trust.json](../../packaging/core-nonproduction-trust.json). Its public seed grants no Release authority. Signing belongs to release preparation. SpaceTerm Core never signs anything.

A Release SpaceTerm Core fetches its feed directly, or through the one HTTP proxy that `spaceterm setup --update-proxy http://HOST:PORT` sets. `--update-proxy off` removes it. The setting lives in the Core's data directory, and the next check uses it. SpaceTerm Core never reads proxy variables from its environment, because a service manager does not pass on a login shell's environment. The proxy address carries no credentials, path or query.

Each finished check sets `check` in the Core's update facts. A check either succeeded at a time, or has been failing since the first failure after the last success, with the latest reason: the network, the proxy, verification, or a system older than the release needs. The state survives restarts, so a stopped Core reports its last check.

An install from the feed that fails records an install failure in the update facts, and the next check tries again. A push that breaks off tells only its sender. A completed push that fails verification records an install failure.

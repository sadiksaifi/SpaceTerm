# Own System Permissions in the SpaceTerm Core package

macOS attributes a program's privacy checks to its responsible process. launchd makes a LaunchAgent its own responsible process, and the shells and programs it starts inherit that responsibility. Programs in a Terminal Session therefore receive the grants of their SpaceTerm Core, not of a desktop that presents them. SpaceTerm Core holds microphone, camera, Screen Recording and Accessibility, which System Settings calls Device Control from macOS 27. Notifications are not among them: the desktop posts them under its own authorization, as [ADR 0063](0063-own-notification-authorization-in-the-desktop.md) records. Apple DTS describes the attribution in [forum thread 756510](https://developer.apple.com/forums/thread/756510): a launchd job "should include `AssociatedBundleIdentifiers`" to name another app, and "the exact algorithm it uses for this is not documented". Disclaiming responsibility for a child is private API, so SpaceTerm does not use it.

## Package

TCC tracks a bare executable by its path. Each SpaceTerm Core version lives at its own `installations/<digest>` path under [ADR 0040](0040-install-core-versions-from-the-feed-a-push-or-a-local-archive.md), so a bare executable would lose its grants on every update. TCC tracks a bundle by its identifier and checks the designated requirement recorded at grant time. The macOS SpaceTerm Core package is therefore an app-like bundle, as Apple recommends for daemons in [Signing a daemon with a restricted entitlement](https://developer.apple.com/documentation/xcode/signing-a-daemon-with-a-restricted-entitlement). Each identity has its own bundle, named for its product: `SpaceTerm Core.app`, `SpaceTerm Core Preflight.app` or `SpaceTerm Core Development.app`. Each holds `Contents/MacOS/spaceterm` and `Contents/Resources`. Its bundle identifier and code signing identifier are both `com.peblon.<identity>.core`. It differs from the desktop's, so the two hold separate grants. [The tracked Info.plist](../../packaging/macos/core/Info.plist) carries the usage strings TCC requires before it prompts, and `LSUIElement`.

A person sees the product's name, "SpaceTerm Core", "SpaceTerm Core Preflight" or "SpaceTerm Core Development", in privacy prompts and System Settings. Those surfaces show the bundle's Launch Services display name: its directory name, not `CFBundleName` or `CFBundleDisplayName`. A prompt showed the bundle's directory name with its ".app" suffix while both keys held another name, and `NSFileManager displayNameAtPath:` returns the directory name for bundles whose keys differ from it. The directory therefore carries the product name. [Apple's File System Programming Guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html) states that "the system hides filename extensions for all files by default". A person who turned on "Show all filename extensions" sees ".app" after every app's name, this one included. Linux keeps `bin/spaceterm` beside `share/spaceterm`. [The layout module](../../crates/spaceterm-core/src/service/runtime/layout.rs) and [the packaging script](../../mise-tasks/lib/spaceterm_tasks/core_package.py) own both layouts.

Login Items & Extensions lists the LaunchAgent under the same name. Each SpaceTerm Core plist, the server's and the recovery agent's, carries `AssociatedBundleIdentifiers` naming the identity's bundle identifier. Without the key, macOS 27 lists the agent under the organization name of its signing certificate, with a blank icon. Login Items attributes a plist path once, when it first registers that path. On macOS 27.0.1, adding the key afterwards changed only the icon, through an in-place edit, a `launchctl` reload, a delete and rewrite at the same path, and a logout. The key is therefore in the plist from its first write. Before SpaceTerm Core installs its plist or replaces it for another installation, it registers that installation's bundle with Launch Services, so Login Items can resolve the identifier. A failed registration fails the installation before the plist exists, so a passing failure can't leave the fallback name on the path. Login Items ignores the key for the ad hoc signed Preflight and Development packages. On macOS 27 it lists their agent as "spaceterm" with "Item from unidentified developer", so only a Developer ID signed Release package shows the bundle's name. [The macOS service module](../../crates/spaceterm-core/src/service/macos.rs) owns both plists.

[TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) states that "macOS checks that this version of the app satisfies the original DR". Release SpaceTerm Core bundles are Developer ID signed. Their designated requirement, `identifier "com.peblon.spaceterm.core"` and Apple's Developer ID requirement for the release Team ID, is the same in every version and for every certificate the team holds, so a grant survives an update. [The signing module](../../mise-tasks/lib/spaceterm_tasks/macos_codesign.py) owns that requirement and the signing order. Preflight and Development SpaceTerm Core packages are signed ad hoc, so their requirement names one build's code directory hash, and each new build loses the grant. Permission Setup then removes the stale entry. The foreground Development SpaceTerm Core runs as a child of `mise run development`, so it inherits the grants of the terminal application that started that command.

Every SpaceTerm Core bundle runs under the hardened runtime. The hardened runtime denies a protected resource to a responsible process without the matching entitlement, and shows no prompt. [The Core entitlements](../../packaging/macos/core/Entitlements.plist) therefore grant the microphone, camera, Apple Events, Contacts, Calendars, Photos and Location, and the Info.plist carries a usage string for each and for Local Network. Screen Recording, Accessibility and Local Network need no entitlement.

## Operations

[SpaceTerm Core's System Permissions](../../crates/spaceterm-core/src/permissions.rs) are the only code that reads, requests or resets these grants.

- **Reads.** A read runs in a probe child, `spaceterm internal permission-report`. The child inherits SpaceTerm Core's responsibility, and a fresh process holds no cached Screen Recording answer.
- **Requests.** A request runs in SpaceTerm Core itself. For the microphone and camera it calls `AVCaptureDevice requestAccessForMediaType:`. A program in a Terminal Session that asks for either device itself gets the same prompt, which names SpaceTerm Core, because its Info.plist carries both usage strings. For Screen Recording it calls `CGRequestScreenCaptureAccess`. For Accessibility it calls `AXIsProcessTrustedWithOptions` with the prompt option. Each request lists SpaceTerm Core in System Settings and may show the system's own prompt. launchd starts SpaceTerm Core without Launch Services, so before a request SpaceTerm Core registers its own bundle with `LSRegisterURL`, which lets System Settings name its entry. An Aqua LaunchAgent belongs to the GUI login session, so its prompts appear there. [TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html) describes Aqua agents as having "access to all GUI services".
- **Opening System Settings.** The client the person uses opens the privacy list: the desktop through `NSWorkspace`, and the CLI through `/usr/bin/open`. macOS brings an application forward only at the request of the active application, and a background SpaceTerm Core is never active. Opening a list changes no grant, so [the permissions module](../../crates/spaceterm-core/src/permissions.rs) only names the list in `settings_uri`.
- **Resets.** A reset runs `/usr/bin/tccutil reset <service> <bundle identifier>`. It runs only while launchd runs SpaceTerm Core from its own bundle, so it never reaches another application's grant.

A Permission Setup asks SpaceTerm Core to clear its stale entry and opens System Settings at its list. The Setup Guide offers SpaceTerm Core's bundle as a row to drag into that list, as the desktop offered its own bundle before SpaceTerm Core held the grants. A request would list SpaceTerm Core turned off, among rows System Settings sorts by name, and raise the system's own alert. The bundle lies in a hidden directory, so the list's + button cannot reach it. SpaceTerm Core reports the bundle's path with its holder. A person who cannot drag chooses List Instead, which requests the permission so System Settings lists SpaceTerm Core turned off, and the guide names it to turn on. An application that holds the grants for a Development server has no bundle to offer, so that setup requests the permission and names the entry to turn on.

## Only on the Machine itself

These grants are set up only on the Machine itself, through that computer's desktop Settings or its `spaceterm` CLI.

- **Service lane.** The lane carries `permissions`, `request_permission`, `prepare_permission_setup`, `cancel_permission_setup` and `reset_permission`. A Permission Setup carries a random setup name. Cancelling it sends `cancel_permission_setup` over another connection, and SpaceTerm Core reads that cancellation again immediately before its reset and, after registering its bundle, immediately before its request, so no prompt appears after the person cancelled. [The setup admission](../../crates/spaceterm-core/src/service/lane/setups.rs) keeps a cancellation until its preparation ends. It bounds admission rather than evicting cancellations: at most four preparations run at once, further ones are refused as `service_busy`, and a cancellation that arrives before its preparation expires after ten seconds. [The lane](../../crates/spaceterm-core/src/service/lane.rs) answers them only for an account-local caller. It refuses a paired caller with `local_only` before the system is asked anything.
- **CLI.** `spaceterm permissions` shows each permission's state and who holds it. `request PERMISSION` asks SpaceTerm Core for one permission, and `settings PERMISSION` opens its list from the CLI. [Route validation](../../crates/spaceterm-cli/src/connection/route.rs) refuses a remote `--machine` with `local_only` before any credential or transport is opened.
- **Desktop.** Settings > Privacy presents the grants of This Mac through [the desktop adapter](../../src/platform/core_permission_access.rs), and a paired Machine's card offers none.

As [ADR 0027](0027-trust-paired-clients-equally.md) says of every action that runs only on the Machine itself, this is not a security boundary. It keeps setup where System Settings and the prompts appear.

Linux has no TCC. Its SpaceTerm Core answers these requests with `unsupported`, and its desktop composes no permission rows.

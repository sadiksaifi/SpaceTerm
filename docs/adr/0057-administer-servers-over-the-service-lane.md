# Administer SpaceTerm Core over the service lane

Status, update facts, installs, Restart, Change Network Access, Remove Machine's Uninstall and the Command Line Tool use a service lane on the authenticated account-local or paired connection. Stop uses the same lane on the account-local connection only. The lane also answers System Permission requests, for account-local callers only, under [ADR 0061](0061-own-system-permissions-in-the-server-package.md). [ADR 0027](0027-trust-paired-clients-equally.md) owns authority and the actions that run only on the Machine itself. `unpair` accepts only the local route, including when the target is another Paired Device. End All Sessions uses account-local work admission under [ADR 0048](0048-end-all-sessions-from-the-selected-servers-settings.md). [CLI route validation](../../crates/spaceterm-cli/src/connection/route.rs) rejects a paired route for `stop`, `unpair` and `end-all-sessions` with `local_only` before credential or transport access.

The lane uses bounded length-prefixed JSON through the admission preamble and negotiates its own version, independently of the work protocol's. A client whose work protocol is too old can therefore update SpaceTerm Core and settle the same operation after reconnecting. This is one lane on the existing transport. [ADR 0035](0035-negotiate-protocol-versions-per-connection.md) owns its version policy. [The lane contract](../../crates/spaceterm-core/src/service/lane.rs) includes the admitting `boot` in `Accepted` and the Pending Version's `to_major` in update effects. Clients use those fields to check replacement and warn when work commands will need a matching client.

[The direct host](../../crates/spaceterm-core/src/direct/host.rs) registers a paired service lane with its pairing's connections before the first request. The registration lasts for the lane's whole life. Revoking the pairing severs the lane. A Network Access change that starts a new listener generation also severs it. [The lane's Core side](../../crates/spaceterm-core/src/service/lane.rs) revalidates the pairing and listener generation before each read and again before answering each request. Host stop severs a waiting lane read before joining its thread.

A lane Status, Facts or Check request reads facts without activation recovery. [`start`](../../crates/spaceterm-core/src/service.rs) settles interrupted activation. Unreachability does not establish that SpaceTerm Core is stopped; any last-known connection time is explicitly dated under [ADR 0058](0058-derive-agent-identities-at-admission.md). Installing a Pending Version ends nothing, so it has no preview: `StageFetch` installs the release the Core's own feed names, and `StageUpload` with `UploadChunk` installs a pushed archive. SpaceTerm Core verifies the Pending Version under [ADR 0040](0040-install-core-versions-from-the-feed-a-push-or-a-local-archive.md).

[ADR 0040](0040-install-core-versions-from-the-feed-a-push-or-a-local-archive.md) owns the feed a Release SpaceTerm Core checks, its signatures and the order in which every source installs.

A running SpaceTerm Core's preview binds an actor, action, Machine, boot, service state or activation approval, and exact affected Terminal Session set. [The lane observation digest](../../crates/spaceterm-core/src/service/lane.rs) hashes those service observations and the sorted Session IDs when the service is running. A Restart into a Pending Version binds the activation approval's confirmation digest; Stop and a Restart into the running version bind the retained service state. SpaceTerm Core retains at most 16 random `c1-` tokens, each redeemable once by its actor and action within ten minutes. An Execute that another unsettled operation refuses with `service_busy` admits nothing and keeps its token, so the same approval can admit the action once that operation settles. Issuing past capacity drops the oldest token. Restarting SpaceTerm Core loses the registry. [The token registry](../../crates/spaceterm-core/src/service/tokens.rs) refuses unknown, spent, expired or mismatched tokens as `changed`.

Unpair and End All Sessions on the Machine itself use `c1-` tokens instead of the token registry SpaceTerm Core holds. [Offline tokens](../../crates/spaceterm-cli/src/admin/offline_token.rs) carry their issue time and a digest binding that time, purpose and exact observation. [Unpair](../../crates/spaceterm-cli/src/admin/unpair.rs) hashes the Machine ID, exact pairing ID and device public key. Each command recomputes its digest before acting. These tokens expire after ten minutes. Expiry or a changed observation reports `changed`.

Admission revalidates the preview and durably records the operation while holding the pane-service lock. It sets the membership fence under that same lock. While any admitted Stop, Restart or Update remains unsettled, [the host request path](../../crates/spaceterm-core/src/host.rs) refuses every `Claim` with `ServiceBusy`, exposed as `service_busy`. This includes reattaching to an already running Terminal Session. Organization edits that start no Terminal Session remain available. This is the v1 membership policy. Repeating the operation ID resolves that record and never repeats the action. The lane writes `Accepted` before launching the helper. A failed write still launches the durably admitted operation.

The approved runtime launches a transient helper outside the SpaceTerm Core service's process tree: a collected systemd user unit on Linux, or `posix_spawn` with `POSIX_SPAWN_SETSID` on macOS. It inherits no SpaceTerm Core sockets or lock descriptors. [The helper](../../crates/spaceterm-core/src/service/helper.rs) holds `service-helper.lock` for its whole run, reads only its admitted record and runs the same native operation as a local caller under the service lock. A free helper lock proves that no helper is acting when [ledger settlement](../../crates/spaceterm-core/src/service/operations.rs) examines an interrupted operation. A recovery helper, launched without a record by a Core that boots into an activation a reboot interrupted, holds the same lock and finishes that activation. No permanent helper is installed.

The durable ledger records admission, launch, execution and the terminal outcome. Startup recovery marks an admitted operation that never launched as not performed. Interrupted Update resolves through activation recovery; an unprovable Stop or Restart stays unresolved. A restart SpaceTerm Core decides on itself is recorded with the Core as its actor, and settlement forgets it once it is terminal, because no client acknowledges it. A changed boot alone is not a generic success receipt. Unacknowledged records remain until the same actor acknowledges them. Revoking the pairing deletes its settled records. An unsettled record stays, orphaned, until its helper or start-up recovery settles it, and the ledger then deletes it. [The shared revocation path](../../crates/spaceterm-core/src/direct/host.rs) invokes [the host's ledger cleanup](../../crates/spaceterm-core/src/host.rs) for both account-local and paired-wire revocation. The ledger refuses new admissions at capacity instead of expiring records by age.

[The shared administration steps](../../crates/spaceterm-core/src/service/lane/admin.rs) wait up to 180 seconds through `service_busy` for a preview and for an approved Execute, on a connection that survives the window that asked. They execute the original token again each time under one journaled operation ID, so a changed observation reports `changed` and the person reviews a fresh confirmation, and a request whose reply was lost can only admit under the ID the caller follows. After such a loss, `service_busy` proves nothing about the first request, so the client keeps following that ID instead of retiring it. One absolute deadline the caller sets bounds opening the lane and its admission, settling earlier operations, the client's waits for its operation record and for its share of its state, the stale-lane redial and every paired dial, the service-lock wait of a stopped Core's confirmation, every preview, Execute and receipt read. No byte of `Execute` is written once that deadline has passed, even by lane I/O the caller stopped waiting for, because each transport reads the clock again before each write, so a deadline that passes before the first `Execute` dispatches nothing, records nothing, and reports `timeout`. An `Execute` that was written keeps its operation ID and settles as an unconfirmed outcome when no receipt arrives in time. Capacity and an unresolved activation never wait. [The lane client](../../crates/spaceterm-core/src/service/lane/client.rs) replaces a lane idle for at least 20 seconds before sending Execute. After a transport loss once Execute was sent, it follows the same operation ID. Before interruption, it can repeat Execute to recover the existing admission. After interruption, it only resolves that ID under [ADR 0055](0055-define-the-cli-output-contract-and-scope-model.md). Restart and Update resolve their receipt before reporting completion. A Stop loses its lane when SpaceTerm Core exits, so the lane client reports the outcome `Shutdown`. [Local Stop confirmation](../../crates/spaceterm-cli/src/admin/lifecycle.rs) then reads the ledger and exits 0 when it records completion. Otherwise the result stays `observed: shutdown` with exit 7, because losing the connection cannot prove native cleanup. The desktop reads the same ledger record. The desktop runs at most one approved Stop or Restart on each Machine. A second confirmation that another surface opened before the first approval admits nothing when approved, and its own surface reports that another operation is running. [The desktop's Machine store](../../src/updates/machines/store.rs) names each preview and each execution as a request: an outcome reaches only the surface of its request, and a wait for another operation shows only for its own request, from when it begins until the preview answers or SpaceTerm Core admits the action. A Stop whose record shows no outcome, and any operation whose receipt never settled, reports an unconfirmed outcome that offers Check Status for that exact operation, which reads what happened and never repeats the action. Try Again appears only after a confirmed failure or a refusal that admitted nothing. A later lane connection after local Start settles and acknowledges a retained receipt. That connection resolves every retained operation before it acknowledges any, so a failed read loses no outcome, and a failed acknowledgement still returns the outcomes acknowledged before it. SpaceTerm Core forgets a receipt before its `Acknowledged` reply leaves, so the client keeps each settled outcome in [its route and identity's record](../../crates/spaceterm-core/src/service/lane/admin.rs) before it sends `Acknowledge`. Check Status on every surface, and a later connection that finds the receipt gone, read that kept outcome. A flow that follows an operation it recorded holds a shared claim beside the record until it returns. Another connection of the same route and identity, such as a concurrent `status` or Check Status, acknowledges a receipt only under the exclusive claim, so it never acknowledges a receipt a running flow still waits to read. [ADR 0034](0034-confirm-server-update-restarts-and-explain-incompatibility.md) owns restart confirmation, a breaking Pending Version and the automatic return to the previous version.

Service 1.4 reads, installs and uninstalls the Machine's Command Line Tool in one step each, with no preview, ledger record or helper, because each changes only the account's own `~/.local/bin` link and ends nothing. The running SpaceTerm Core answers them in-process through the same `Service::cli_launcher`, `Service::link_cli` and `Service::unlink_cli` the desktop uses on its own computer under [ADR 0054](0054-use-one-headless-executable.md), so install follows the approved runtime, refuses without one, and leaves another program's entry in place. The desktop sends them only to a Core that selected 1.4 or later and otherwise says the Machine needs a newer SpaceTerm Core.

## Network Access changes

`spaceterm network` changes Network Access through the lane, on the account-local or paired route. `setup --network` stays on the Machine itself. [The lane's Network Access module](../../crates/spaceterm-core/src/service/lane/network.rs) owns the plan, its refusal and its observation digest. [The direct host](../../crates/spaceterm-core/src/direct/host/network_change.rs) plans each change under its direct-network lock. A plan holds Network Access before and after the change, whether the listener starts over and so ends every paired connection, and which connected Paired Devices lose their route. A connection keeps its route when the new listener serves the Machine address it reached. The preview reports the caller's own connection as `stays_connected`, `reconnects` or `disconnected`.

A paired caller's change that keeps no connected device's route is refused as `disconnects_every_device`, before any token is issued. Turning Network Access off is always such a change. SpaceTerm Core cannot see the routes of devices that are not connected, so they do not count. The account-local route may make any change.

The token binds the SpaceTerm Core run, the request, both settings, the listener generation and every reported effect. The devices that keep a route are not in the digest. Execute plans again under the direct-network lock, checks the token's digest and the refusal, and admits the change in the ledger. The lane writes `Accepted`, then plans once more and checks the digest and the refusal again in the same hold, because a device may disconnect or be revoked meanwhile. A refusal then settles the record as failed with `disconnects_every_device`. Otherwise the lane claims the record and applies the change in-process with the same `SetPolicy` request that `setup --network` sends. A listener that fails to bind settles it as failed with `address_unavailable`, and nothing changed. A change that turns access on settles as done only once its listener accepts. A narrowing that waits for the listener it replaces to retire settles on a watcher thread, because the lane's own thread may hold one of that listener's connections. The watcher follows the listener generation and address the change applied, read in the same hold. It settles the record as done when that listener accepts, and as unresolved when it stops, when a later policy change replaces it first, or when [`LISTEN_LIMIT`](../../crates/spaceterm-core/src/service/lane/network.rs) passes: the five-second retirement bound, the ten-second stall limit and two seconds more. No helper runs. A Network Access change ends no Terminal Session, so it sets no membership fence. A SpaceTerm Core that ends between the claim and the recorded outcome leaves the record unresolved; one that ends before the claim leaves it not performed.

When the change ends the caller's lane, [the lane client](../../crates/spaceterm-core/src/service/lane/client.rs) reconnects and resolves the same operation ID, as it does after a Restart. [The command](../../crates/spaceterm-cli/src/admin/network.rs) then reads Network Access back over a new connection. A caller that lost its route cannot reconnect, so the command reports `outcome_unconfirmed` and exits 7 when its wait ends. [The shared administration steps](../../crates/spaceterm-core/src/service/lane/admin.rs) follow a Network Access change for 30 seconds, which covers `LISTEN_LIMIT` and a reconnect, rather than the 180 seconds a SpaceTerm Core that replaces itself needs. The desktop makes no Network Access change and names one only as an earlier settled operation. Its settled record stays in SpaceTerm Core until that device acknowledges it on a later connection or is unpaired.

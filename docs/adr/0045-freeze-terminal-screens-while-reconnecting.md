# Freeze terminal screens while reconnecting

When a SpaceTerm Client unexpectedly loses its server connection, it keeps its last displayed terminal screen visibly frozen with "Reconnecting..." and a Retry action. Automatic reconnect uses bounded backoff while terminal input remains disabled. Interrupted input is discarded and never replayed.

Before enabling input, the client reconciles [authoritative server state](0036-publish-workspace-changes-to-connected-clients.md) and verifies [Pane control](0022-give-one-client-control-of-each-pane.md). Another client's takeover remains effective. A Takeover Screen remains visible throughout the interruption without revealing an older terminal screen, and reconnect never takes over automatically.

Reconnect validates the original server and build identity with the admitting route's authority under [ADR 0027](0027-trust-paired-clients-equally.md). A stable nonsecret Client Identity retains personal views, attachments and eligible control across relaunch; it supplies no connection authorization. Local reconnect uses owning-account authority without native credential access. SSH continuation and restricted original-operation resolution follow [ADR 0029](0029-pair-clients-automatically-during-ssh-bootstrap.md). Direct-network continuation retains paired-device authority and verified server trust. Background continuation defers interactive authentication and provider consent to requested remote work or Connect/Resume.

SSH continuation belongs to one worker for the requested connection intent. Transient transport loss and sleep permit bounded retry backoff; authentication, host, account or server changes pause it. Previously active intent may be restored quietly after client relaunch. Merely saving a host, constructing its row or opening Settings grants no connection intent. Disconnect, connection removal and deliberate Stop end ordinary retries. Fresh interaction requires requested remote work or Connect/Resume and never renews a destructive operation's approval.

# Use one headless executable

`spaceterm` runs SpaceTerm Core's account service and provides the command-line client for This Mac or This Computer and paired Machines. It links no GPUI, GPU, display or Sparkle code, so administering SpaceTerm Core and terminal work need no desktop process. The desktop remains a separate executable under [ADR 0012](0012-derive-one-application-identity-from-the-build.md).

The signed headless artifact contains `server/bin/spaceterm` on Linux and an app-like bundle, `server/SpaceTerm Core.app/Contents/MacOS/spaceterm` for Release, on macOS. [ADR 0061](0061-own-system-permissions-in-the-server-package.md) explains the bundle. Native service units invoke `spaceterm internal serve --service --identity <identity>` from the approved runtime. The foreground Development supervisor uses `internal serve --owned`; service and owned modes are mutually exclusive. The transient service helper uses hidden `internal helper`. Installer and SSH Setup provisioning, runtime verification and packaging checks use the other hidden `internal` commands. [The command tree](../../crates/spaceterm-cli/src/args.rs) owns this grammar. The CLI opens no SSH connection; [SSH Setup](0003-use-openssh-for-server-setup.md) remains a desktop operation.

The installer owns the command-line launcher in `~/.local/bin/`. It points to the approved runtime, or to the installation just retained when none is approved. [Launcher replacement](../../crates/spaceterm-core/src/service/runtime/launcher.rs) holds the service lock and replaces only a link into that identity's installations. A foreign executable or link stays untouched. `spaceterm uninstall [--delete-data] [--confirm TOKEN]` stops and unregisters the service and removes only its managed launcher under that lock. It keeps Workspace organization, Machine Settings, pairings and the CLI's Saved Connections unless `--delete-data` is given. `install.sh --headless --uninstall` runs it. [The local workflow](../local-server.md#install-spaceterm-core) documents its preview and confirmation. Desktop and headless installation share one SpaceTerm Core under [ADR 0033](0033-reuse-one-server-across-headless-and-desktop-installations.md).

The service lock orders only SpaceTerm's own writers. The installer and the desktop create a missing launcher exclusively, so an entry another program creates first stays and is reported as occupied. They replace SpaceTerm's own managed link by renaming a new link over it from the fixed name `.launcher-<identity>`. Under the lock, a leftover there from an interrupted replacement is removed before the next replacement and on uninstall, but only when it is a link into that identity's installations. Another program's entry there stays and blocks the replacement; the Command Line Tool row reports the launcher as blocked and offers to show that entry. POSIX has no atomic compare-and-replace, so a program that writes this exact SpaceTerm-named path between the check and the rename loses its entry; SpaceTerm accepts that window. Repointing an existing managed launcher after installation or an update never stops the service or the Pending Version. A failure leaves the link on its earlier installation. The Command Line Tool row reads the launcher again whenever the desktop learns that a service operation or update finished, and then shows it as out of date with Reinstall.

The desktop's Settings > Machines presents this launcher as the Command Line Tool row. Its Install uses the same launcher replacement through `Service::link_cli`. That call waits at most the one-second operation grace for the service lock, then reports a busy service. It follows the approved runtime. Without one, it first retains the desktop's own signed SpaceTerm Core package, which registers and starts no service. Install writes only the account's own `~/.local/bin`, so it needs no administrator authorization, password or credential store. A link elsewhere and a file that is not a link stay untouched; the row names either and offers to show it in the file manager, which reports whether it could. The row makes no claim about PATH or about which command a shell resolves. It states that terminals run the command by name when `~/.local/bin` is on PATH. Learning PATH would mean running the person's shell startup files, which can read the Keychain, call a password manager or open protected folders, and so show prompts credited to SpaceTerm; SpaceTerm runs no shell for this and edits no shell profile. [The Command Line Tool module](../../src/command_line_tool.rs) owns the row's states and refusals.

[Signing] Developer ID, hardened runtime, notarization, the installer's requirement check and team pinning are future work; none is required for this executable split.

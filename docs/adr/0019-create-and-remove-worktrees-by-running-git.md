# Create and remove Worktrees by running git

The owning SpaceTerm Core creates and removes Worktrees by running the person's own git with the hardening Repository Status reads use, so git stays the one owner of the repository's administrative files. These are SpaceTerm's only repository writes, and they happen only when the person confirms one in a dialog. Writes use branches already fetched, and git itself never fetches, because every transport is disabled. Worktree paths and repository authority belong to that Machine's filesystem for local and remote Workspaces. Hooks never run, so a `post-checkout` hook's setup does not happen. Clean and smudge filters run under the person's configuration, as they do for reads, so a filter such as Git LFS can download content while a Worktree is created. Removing a Worktree passes `--force` only after the person confirms an alert that names what it deletes: uncommitted changes they chose to discard, or the checkouts of the Worktree's submodules, which git removes only with `--force`.

A started write runs independently of its client's connection, with a two-minute Git subprocess deadline. After a timeout, Core stops the process group and checks Git and the target directory before it releases deferred edits. Core accepts a verified complete checkout or removal. It reports an interrupted write when verification fails and leaves any partial changes for the person to inspect.
